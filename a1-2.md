As a professional software tester, I would approach this feature using risk-based testing, focusing on identifying defects that could compromise:

* Functionality – Whether the upload feature behaves according to the acceptance criteria.

* Data Integrity – Whether uploaded documents and their associated information remain accurate, complete, and consistent.

* Security – Whether documents are protected against unauthorized access, malicious uploads, and information disclosure.

Below are suggested test ideas grouped by quality characteristics.

### 1\. Functionality

Focus: Verify that the upload feature works correctly under normal, boundary, and exceptional conditions.

| ID  | Test idea                                                             | Expected result                                                                                  |
| --- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| F01 | Upload a valid PDF file below 20MB.                                   | File uploads successfully.                                                                       |
| F02 | Upload a valid DOCX file below 20MB.                                  | File uploads successfully.                                                                       |
| F03 | Upload a valid TXT file below 20MB.                                   | File uploads successfully.                                                                       |
| F04 | Upload a file exactly 20MB.                                           | File uploads successfully.                                                                       |
| F05 | Upload a file slightly larger than 20MB.                              | Upload is rejected with an appropriate error message.                                            |
| F06 | Upload an unsupported file format (e.g., JPG, XLSX, ZIP).             | Upload is rejected with an appropriate error message.                                            |
| F07 | Upload a file with no extension.                                      | Upload is rejected if its format cannot be verified.                                             |
| F08 | Upload an empty file (0 bytes).                                       | System handles the file appropriately without unexpected errors.                                 |
| F09 | Upload multiple documents consecutively.                              | Each document is uploaded and processed correctly.                                               |
| F10 | Observe upload progress during a large file upload.                   | Progress updates are displayed accurately until completion.                                      |
| F11 | Upload a file using a slow network connection.                        | Progress updates continue appropriately, and the upload eventually succeeds or fails gracefully. |
| F12 | Interrupt the network connection during an upload.                    | Upload does not incorrectly report success and provides appropriate feedback.                    |
| F13 | Cancel an upload while it is in progress (if supported).              | Upload is cancelled and the user receives confirmation.                                          |
| F14 | Upload a file with a long filename or special characters in its name. | System handles the filename without errors or unexpected behavior.                               |
| F15 | Upload the same document multiple times.                              | System handles duplicate uploads consistently according to the intended behavior.                |

### 4\. Additional high-priority risk areas

Some tests deserve particular attention because of the sensitive nature of legal documents.

Priority 1 – Cross-user document access

Critical

Verify that one paralegal cannot access another paralegal's documents by manipulating URLs, API parameters, or document identifiers.

Priority 2 – File type validation

Critical

Verify that the server validates actual file content (file signatures/MIME type), not just the file extension. This helps prevent malicious files disguised as legitimate documents.

Priority 3 – File corruption

High

Verify that interrupted uploads cannot result in corrupted documents being marked as successfully uploaded.

Priority 4 – Audit accuracy

High

Verify that both successful and failed uploads are recorded accurately. Audit records should not be easily manipulated or deleted by ordinary users.

Priority 5 – Upload progress accuracy

Medium

Verify that displayed progress corresponds to actual upload progress and does not report 100% before the server confirms successful storage.

### 5\. Important testing considerations

There are a few ambiguities in the acceptance criteria that should be clarified before finalizing the test cases.

| Requirement                           | Clarification needed                                                                                 |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Maximum file size: 20MB               | Is 20MB exactly 20,000,000 bytes or 20 × 1,024 × 1,024 bytes (20 MiB)?                               |
| Supported formats                     | Should the system validate file extensions, MIME types, or actual file signatures?                   |
| Upload progress                       | Does progress indicate bytes transmitted or successful server-side processing?                       |
| Initially only accessible to uploader | Can the uploader explicitly share the document later? Who can revoke access?                         |
| Audit report                          | Which fields must be recorded? Are failed attempts, cancellations, and interrupted uploads included? |
| Duplicate uploads                     | Should duplicate documents be allowed, rejected, or treated as separate versions?                    |

My recommendation: For this feature, prioritize Security and Data Integrity over simple happy-path functionality. A system that successfully uploads a PDF but accidentally exposes confidential legal documents to another user is a much more serious failure than one that displays an incorrect progress percentage.

The test ideas above can serve as a foundation for deriving detailed test cases using equivalence partitioning, boundary value analysis, negative testing, and security testing.
